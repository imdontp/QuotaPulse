# Models opt-in summary reads v1.85.110

GET /api/models?detailed=1&breakdown=0 uses the existing authentication and exact usage scope. Optional trends=1 retains the existing complete trend response. All totals and all model/provider groups retain their original facts, ordering, null/empty/case identities and distinct-session semantics. The per-source/effort rows property is absent and breakdown is explicitly omitted; it is not an empty/truncated breakdown. The extra grouped breakdown query is not executed.

Default detailed=1 and explicit breakdown=1 return the original full shape, including every row and no new breakdown marker. Legacy requests without detailed remain unchanged. Other breakdown values, duplicate values or use without detailed=1 return400; missing authentication stays401. Projects endpoint/defaults are unchanged. Existing full API, selected model-detail effort/context and batch row-trend APIs remain available normally.

The redesigned Models page consumes ModelSummaryResponse, whose type excludes rows. Its rendering already derives from groups/totals/trends and separate selected-model detail. No CSS, chart data floor, displayed count or layout is changed. The previous detailedModels client method is retained.

The new loader first tries the opt-in. On400 only, it tries the exact same full scoped read. Only a successful full read remembers legacy mode until page reload, so subsequent refreshes avoid repeated failed probes. Auth/network/server failures propagate without this retry. Invalid scopes that also fail the full read do not disable summary mode. Older servers that ignore the opt-in still work, and unused rows are removed from UI state without mutating the response. This compatibility path preserves functionality, not the modern network-size improvement. It does not cache facts across scopes or alter existing stale-response guards.

Tests cover an independent frozen SQL oracle across scopes, HTTP totals/groups/trends/full-default parity, malformed flags/auth/read-only data, and modern/legacy/error client transport. Two real Chrome cases (EN dark/TH light) additionally reject the new parameter to simulate an older daemon, verify exact main text, then exercise actual refresh and remembered full reads. The refresh test is permitted only on the private empty-reader fixture; it can mark synthetic sources gone, never opens a user DB. The initial compatibility harness rejected its own intended POST /api/refresh; that whitelist error was corrected without a product workaround, and the failed log is retained.
