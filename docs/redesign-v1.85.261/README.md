# Models: routed provider and model maker

The Models screen contract requires separate provider and vendor filters and a vendor footer that applies the vendor filter. Previously the footer only grouped recorded routing providers and applied `provider`, so a model reached through a gateway could not be selected there by its maker. The footer now offers **Provider** and **Model maker** views. Provider remains the default; a maker card applies or clears `vendor` while preserving the provider filter and the rest of the scope. Both views retain the recorded model/provider-pair counts and scoped token shares.

The daemon's opt-in model trend response now adds per-maker token histories, classified by the same model/provider rule used for model groups and filters. The query first groups exact model/provider/time buckets before classifying them. Existing responses without `trends=1` are unchanged. When a newer web client receives a trend response from an older daemon without maker histories, it shows the known aggregate share as a bar instead of inventing historical samples.

[Compare the two views and the concept](review.html). Captures use a fixed synthetic fixture at 1672 × 941, English/dark, DPR 1 and reduced motion; they do not contain user data or certify visual parity. The maker-mode capture repeated byte-for-byte. `capture-verification.json` records its build and image hashes.

Daemon and web builds passed, as did 160 daemon and 383 web tests. The existing `npm run test:ui` compatibility suite, run before the focus change, passed its navigation, loading, responsive and popup checks. The Models browser suite passed EN/TH × dark/light, with 390/900/1280/1672 responsive checks. In an isolated synthetic fixture where GPT-5.x was routed through both OpenAI and OpenRouter, keyboard selection of OpenAI maker kept both routes, preserved an independently selected provider when used together, and cleared only the selected maker. It also verified API-matched history, full accessible names, and fallback for a response without maker histories. Keyboard focus returned to the activated card after a filter change and stayed in search when moved during a delayed response. Two of four screenshot pairs were byte-identical. The remaining two passed the recorded unmasked raster tolerance. `browser-result.json` records these checks.

A local in-memory SQLite benchmark of the complete model-history query over 50,000 synthetic rows, five alternating runs after warm-up, measured medians of 63.4ms before and 99.9ms after. Results and timings are in `benchmark.json`; they are specific to this fixture and machine, not production performance certification. The extra grouping query increases work and should be evaluated on representative real workloads.

Review257 predates this change. Real-provider operation, physical/native behavior, broader performance and full concept/release acceptance remain open.
