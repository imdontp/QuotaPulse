# Preserve sources when detection fails

A synthetic regression reproduced a source disappearing from the enabled source list when its adapter's `detect()` threw: the runner logged the error, treated the failed result like an empty successful result, and disabled the source. The same pass correctly disabled a different source whose adapter actually returned an empty list. This established the failure in an isolated test, not its frequency in customer installations.

Only a successful detector can now establish that one of its sources is absent. A source belonging to a failed or unattempted detector retains its last enabled state, but an unverified profile is excluded from that pass and is not read until detection succeeds. A separate `(detection)` diagnostic is recorded against previously enabled sources and cleared on successful detection; it does not include the underlying error text or overwrite read-error records. Previously unseen sources cannot receive a source-specific diagnostic until they have first been detected.

The harness health endpoint surfaces this diagnostic. Its existing account-only reader exclusion remains: account-only detection errors are recorded but are not surfaced by that endpoint. A retained enabled flag is the last known state, not proof that the source is currently present. A detector that returns an empty result while suppressing its own error is indistinguishable from successful absence and is outside this correction. Source-level detection alone also does not prove complete ingestion, so the Cost projection remains unavailable.

Validation: the original isolated reproduction failed before the change and passed afterwards. Sixteen focused source/scheduler tests passed, including a failed detector beside a successful empty result, scoped detection, diagnostic recovery, and manual refresh pause/resume. The daemon build and all 143 daemon tests passed. The latest review218 package predates this change; no native package or actual customer account was tested for this checkpoint.
